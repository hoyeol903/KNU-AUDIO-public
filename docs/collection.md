# 공지 수집 실행

같은 DB를 쓰는 수집 명령은 하나씩 실행한다. JSON 교체는 원자적이지만 여러 프로세스의 동시 갱신을 잠그는 기능은 없다. 운영 자동화도 단일 writer로 실행한다.

## 일일 입력 파일

`python -m collector.run --write-items`로 수집 후 오늘 신규·마감 알림을 채널별 items.json에 저장한다. 기존 DB만으로 만드는 명령은 `python -m collector.daily_items`이며 실행 보고서의 오류도 전달하려면 --collection-report를 지정한다. 실제 결과·샘플·미수집 항목·한계는 docs/daily-items.md를 읽는다.

## 실행

프로젝트 루트에서:

```bash
python -m collector.run
# 현재 로컬 환경
/opt/anaconda3/bin/python3 -m collector.run
```

기본 실행은 학교 학사공지(`knu-academic`), 전자공학부 공지(`notice-df44dd8507c1`), 국어국문학과 학사공지(`notice-6c1f8a512fa4`), 영어영문학과 학부공지(`notice-1abc9573202c`), 수학과 공지사항(`notice-472ae4378387`) 5개 채널의 **daily 모드**다. 학교·전자공학부의 결과와 공지 예시는 `docs/public-notices.md`를 읽는다. `--channel-id`를 반복 지정해 검증된 추가 채널도 선택한다. `--required-knu-cms`로 검증된 필수 KNU CMS 전체를 선택할 수 있다. 상세 결과는 `docs/knu-cms-expansion.md`를 참고한다. 남은 필수 6개 채널의 지원과 실행법은 `docs/remaining-notices.md`에 있다. 선택 채널 전체와 주소 미확인 조직은 아직 지원 범위 밖이다.

- `--mode daily`: 최근 30일 구간을 확인한다. 일반 공지가 모두 30일보다 오래된 페이지가 2번 연속 나오면 멈춘다. 고정글은 경계 판단에서 제외한다. 날짜 미확인 글이 있는 페이지는 경계를 끊는다. 범위 밖의 저장된 마감 예정·날짜 미확인·needs-review 글도 상세를 따로 확인한다.
- `daily`는 자동으로 전체 목록 점검으로 전환되지 않는다. 오래된 목록 뒤쪽의 새 글·수정 확인은 자동 수집 범위에서 보장되지 않으며, 확인이 필요하면 `python -m collector.run --mode full`을 실행한다. 실패한 수동 전체 점검은 성공 시각을 갱신하지 않는다.
- `--mode full`: 전체 목록을 순회한다. 오래된 일반 글의 상세는 마지막 성공 확인 후 7일 이상일 때 다시 받는다.
- `--mode start`: 새로운 게시판의 최근 구간으로 운영을 시작한다. 기존 적재분을 오늘 신규로 만들지 않고, 과거 전체 확인 시각은 기록하지 않는다. 이미 운영 중인 게시판에는 사용할 수 없다.
- `--mode init`: 과거 적재용이다. 처음 보는 게시판도 자동으로 init 처리한다. 정상적으로 전체를 확인해야 운영 기준 시각이 저장된다. 오류·페이지 제한·중단이 발생하면 초기화 완료로 표시하지 않는다.

기본 최대 1000페이지이며 `--max-pages N`으로 제한한다. 정상적인 일일 경계 도달은 `window_complete: true`, `truncated: false`다. 다음 페이지가 남아 있는데 상한에 도달하면 `truncated: true`, 종료 코드 1이다. 일일 범위는 전체 게시판을 매일 확인했다는 뜻이 아니다.

- 저장: `data/db/notices.json`
- 운영 기준: `data/db/notices-collection-state.json` (사용자 지정 DB는 같은 폴더의 `<DB stem>-collection-state.json`)
- 실행별 보고서: `data/runs/<실행시각>-channels.json`
- 테스트 저장 경로 지정: `--db-path /tmp/knu-notices.json --report-path /tmp/knu-report.json`

보고서는 수집 범위, 논리 channel_ids, 첫 적재 여부, 목록 수, 상세 성공 수, 신규·수정·동일 글 ID, 실패 주소·이유와 시작/종료 시각을 기록한다. 같은 site/nav_code를 공유하는 채널은 한 번 수집해 함께 연결한다. 실패 또는 페이지 제한으로 중단하면 종료 코드 1, 선택한 확인 범위를 오류 없이 마치면 0이다. 성공한 글은 실패와 별개로 저장한다. 목록·상세 실패는 빈 공지로 저장하지 않는다. 이전에 저장한 긴급·검토 대상은 목록 실패와 별도로 재확인할 수 있다. DB 손상·파일 저장 오류는 실행을 중단하며 빈 DB로 대체하지 않는다.

실패 게시판만 다시 확인하려면 `python -m collector.run --retry-failed --write-items`를 실행한다. 오늘 보고서에서 오류가 있거나 페이지 제한으로 끝난 게시판만 골라 요청하며, 재수집 보고서와 당일 `items.json`은 새로 저장한다. 대상을 명시하려면 저장된 입력을 보존한 채 `--retry-report data/runs/<보고서>.json`을 덧붙인다. 재시도 결과 보고서는 입력 보고서와 다른 파일이어야 한다. 실패 대상이 없으면 네트워크 요청과 파일 저장 없이 종료한다. 수동 전체 수집과 예약 실행은 기존처럼 동작하며, GitHub Actions의 수동 실행 화면에서 `retry_failed` 모드를 선택할 수 있다.

## 요청 규칙

`collector/http.py`가 requests Session 하나로 순차 요청한다. 동시에 여는 연결은 1개다. User-Agent를 명시하고 같은 호스트에 이전 요청이 끝난 뒤 최소 1초를 기다린다. 리다이렉트도 간격을 적용한다. 연결/읽기 타임아웃은 각각 10/30초다. 연결 오류·타임아웃과 HTTP 408/429/500/502/503/504는 추가 재시도 최대 2번, 나머지 HTTP 오류는 즉시 실패한다. Retry-After의 초 단위 값은 기다린다. 리다이렉트는 최대 5번이다. 받은 HTML의 문자 인코딩을 판정해 기존 파서에 전달한다.

## 범위와 다음 단계

현재 학교 학사공지·전자공학부와 검증된 CMS 채널을 지원한다. 전체 조회에는 상세 요청이 많이 필요하므로 초기 검증은 `python -m collector.run --max-pages 2`처럼 범위를 제한할 수 있다. 제한 실행은 전체 수집으로 취급하지 않는다. 일일 목록은 최근 구간과 오래된 일반 글 페이지 2개까지만 확인하고 오래된 상세는 재확인 주기에 따라 생략한다. 이 범위 밖 과거 일반 글의 추가·수정은 자동 수집으로 보장하지 않으며 필요할 때 수동 full로 확인한다. 목록이 이동 도중 변경되면 게시물 누락 가능성이 있어 스냅샷 전체 일관성을 보장하지 않는다.

첫 적재에서 과거 공지도 DB 관점의 `new`로 표시되며 `initial_import: true`를 기록한다. 이는 당일 새 공지라는 뜻이 아니다. 아직 브리핑 입력 생성·마감일 추출·첨부 파일 내용 읽기는 없다. 첨부 링크는 파서 결과에 있고 영구 DB에는 저장하지 않는다.

다음 우선순위는 필수 KNU CMS 학과·단과대의 상세 검증과 수집 확대다. 이후 다른 게시판 틀과 채널별 `items.json`을 준비한다. 매일 자동 실행은 이 흐름이 안정된 후 Actions로 연결한다.

```bash
python -m pytest -q
```

테스트에서는 HTTP 응답과 시간을 대체하고 저장 HTML을 사용하므로 실제 사이트를 호출하지 않는다. 요청 간격·재시도 한도·리다이렉트 인코딩·부분 실패·중복 저장을 확인한다.

## 마감일 자동 판정

상세를 검증한 뒤 collector.deadlines로 명시된 종료 날짜를 읽어 deadline에 저장한다. 모호한 날짜는 deadline_checks와 needs_review에 남긴다. 기존 저장 자료는 `python -m collector.deadlines --apply`로 재분석한다. 원문 근거·실측·한계는 docs/deadlines.md를 읽는다.

## 상세 재확인 정책 (2026-10-01)

| 조건 | 상세 요청 |
|---|---|
| DB에서 처음 보는 글 ID | 게시일과 관계없이 즉시 |
| 게시일이 한국 날짜 기준 오늘−7일 이상 | 매 실행 |
| 확인된 마감일이 오늘 이상 | 매 실행 |
| 게시일 미확인 또는 저장된 본문 needs-review | 매 실행, 검토 대상 |
| 목록 제목·게시일 변경 | 즉시 |
| 그 외 글 (8~30일 된 글 포함) | 마지막 상세 성공 확인 후 7일 이상일 때 |

상단 고정 여부만으로는 오래된 상세를 매일 다시 요청하지 않는다. 고정글도 신규, 최근 게시, 마감 임박, 검토 필요, 목록 변경 또는 7일 재확인 조건에 해당하면 상세를 받는다. 목록 경계 판정에서 고정글을 제외하는 동작은 그대로다.

예: 10월 1일 기준 9월 24일 게시물은 매 실행 상세를 받고, 9월 23일~9월 1일 게시물은 위 예외 조건이 없으면 마지막 상세 성공 확인 후 7일 이상일 때 받는다. 목록 순회는 RECENT_DAYS=30을 유지하고, 상세의 최근 게시물 확인 기준은 DETAIL_RECHECK_DAYS=7을 사용한다. daily_items의 신규 판정도 30일을 유지한다. 여기서 매 실행은 예약 주기와 관계없이 실제 수집 실행을 뜻한다. 7일은 고정 요일이 아니라 마지막 확인 시각부터 경과한 시간이다. 생략한 글의 last_checked_at은 그대로 두고 보고서 skipped에 ID를 기록한다. unchanged는 실제 상세를 받아 내용이 같았던 글만 포함한다. 날짜를 읽지 못한 글은 needs_review에도 기록한다. 날짜 칸이 없거나 형식이 잘못된 HTML은 정상 미확인과 구분해 파싱 오류로 남긴다.

8~30일 된 일반 글의 본문 수정은 7일 재확인 때 반영된다. 매일 같은 시각에 정상 실행하면 최대 약 7일 늦게 반영될 수 있다. 실제 확인 시각이 달라 7일 경과 시점을 지나친 경우 다음 날 실행까지 약 8일 가까이 걸릴 수 있으며, 실행 누락·수집 실패가 있으면 더 늦어진다. 마감이 오늘 이후인 글은 게시일과 관계없이 매 실행 상세를 확인하므로 마감 재안내 후보가 주간 생략 때문에 stale로 빠지지 않는다.

현재 마감일 추출은 미구현이다. DB에 이미 확인된 deadline이 있는 경우 예외 조건에 사용하며, 상세 원문이 같으면 해당 값을 보존한다. 원문이 바뀌고 마감일을 다시 확인하지 못하면 null로 저장하고 needs_review에 표시한다. 첫 적재에서는 오래된 글도 모두 상세를 받으므로 이후 실행보다 요청량이 많다.

전체 오프라인 테스트 45개 통과. 상세 생략 시 DB 및 상세 확인 시각이 변하지 않는 것도 검증했다.

## 3개 학과 검증 (2026-10-01)

```bash
# 기본 5개 채널 전체 목록 점검
python -m collector.run --mode full
# 특정 채널만 선택; 여러 번 지정 가능
python -m collector.run --channel-id notice-1abc9573202c --max-pages 1
```

게시판 ID는 원문 URL의 site와 nav_code로 생성한다. 서로 다른 게시판의 글 번호가 같아도 충돌하지 않는다. 한 HTTP Client를 공유해 학과 사이에도 같은 호스트의 요청 간격을 지킨다. 한 채널의 요청/파싱 실패는 보고서에 남기고 다음 채널로 진행하며, DB 손상·저장 실패는 중단한다.

배치 보고서 최상위는 `channels`(채널별 실행 보고서 배열), `request_count`(실제 HTTP 요청 총수)다. 채널 보고서의 `request_count`는 재시도·리다이렉트를 포함한 요청 시도 수이고 `duration_sec`는 간격 대기·파싱·저장을 포함한 경과 초다. 기존 단일 실행 보고서는 이전 형식 그대로 보존한다.

| 학과 | 확인 범위 | 목록 | 상세 성공 | 상세 생략 | 신규 저장 | 실패 | HTTP 요청 | 경과 초 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 국어국문학과 | 첫 페이지 | 19 | 16 | 3 | 0 | 0 | 17 | 18.288 |
| 영어영문학과 | 첫 페이지 | 12 | 12 | 0 | 12 | 0 | 13 | 14.900 |
| 수학과 | 첫 페이지 | 16 | 16 | 0 | 16 | 0 | 17 | 20.239 |
| 합계 | 첫 페이지 검증 | 47 | 44 | 3 | 28 | 0 | 47 | 53.427 |

## 초기 적재와 당일 신규 구분 (2026-10-01)

`new`는 처음 DB에 저장한 글이다. `bootstrap`은 과거 적재 구간이며 이때 `new_candidates`는 항상 빈 배열이다. 성공한 초기 적재 이후, 최초 발견일이 오늘이고 게시일이 최근 30일인 글만 `new_candidates`로 집계한다. 처음 발견했지만 오래됐거나 게시일이 미확인인 글은 `late_discoveries`에 따로 기록한다. 동일한 날 재실행해도 DB의 first_seen_at으로 후보를 다시 구하므로 중단 전 저장한 신규 발견을 잃지 않는다. 수정 글은 기존 `updated`에 기록하며 자동으로 신규 후보에 넣지 않는다. 실제 일일 items.json 선정은 후속 구현이다.

기존 검증된 4,330개는 운영 기준 시작 전 과거 적재로 등록했다. DB 내용은 변경하지 않았고 기준 등록 근거·시각은 `data/runs/collection-baseline-20261001.json`에 남겼다. 전체 점검 시각은 긴 제목 6건 복구까지 마친 13:44:39 KST를 기준으로 삼았다.

일일 경계는 일반 게시물이 게시일 역순으로 놓인다는 가정이다. 오래된 날짜로 깊은 페이지에 추가한 글과 깊은 과거 글의 본문 수정은 daily 범위에서 보장되지 않는다. 필요한 경우 수동 full로 확인한다. 게시일 순서가 불규칙하거나 수집 중 목록이 이동하면 수동 전체 점검에서도 누락 가능성이 남는다.

```bash
python -m collector.run                  # 일일 최근 구간 확인
python -m collector.run --mode full      # 즉시 전체 목록 점검
python -m collector.run --mode init      # 과거 적재, 신규 후보 제외
python -m pytest -q                      # 오프라인 테스트
```

필수 게시판 전체 초기 적재가 중단되면 마지막 `required-recent-*.json` 보고서를 이어서 실행한다. 보고서에서 정상 완료한 게시판만 건너뛰며, 나머지는 저장된 게시판 상태에 따라 daily/start 모드로 처리한다. 재개 보고서는 새 파일로 저장되고 원본은 유지된다. `request_count`와 `duration_sec`는 이번 실행분이며, 전승한 게시판의 값은 각 채널 기록에 그대로 남는다. 이 도구는 당일 `items.json`을 만들지 않는다.

```bash
python -m tools.collect_required_recent --resume-report data/runs/required-recent-20261001T203347+0900.json
```
