# 데이터 목록과 공지 저장 구조

## 지금 검토할 CSV

`output/csv/`의 파일은 현재 YAML을 펼친 검토용 사본이다. 서비스 설정 기준은 `data/departments.yaml`, `data/channels.yaml`이다. CSV를 수정했다고 서비스 설정이 자동으로 바뀌지는 않는다.

| 파일 | 한 행의 의미 | 현재 행 수 |
|---|---|---:|
| departments.csv | 단과대학 또는 학과·학부·전공 하나 | 183 |
| channels.csv | 공지·식당 채널 하나 또는 주소 미확인 자리표시자 | 222 |
| department_channels.csv | 학과 ID와 현재 필수 채널 ID의 연결 하나 | 462 |

CSV는 UTF-8 BOM, 쉼표 구분, 한글 열 이름으로 저장했다. 목록형 값은 ` ; `로 구분한다. 빈 셀은 미확인 또는 해당 없음이며 숫자 0을 뜻하지 않는다. ID 열은 문자열로 읽는다. 엑셀이나 Numbers에서 열고 필터를 사용하면 된다.

- 조직표는 `검토필요=예`, `운영확인=운영 여부 확인 필요`를 우선 본다. 사용자 제공 주소를 전공별로 연결한 학부는 `전공별게시판`, `연결전공`, `조사메모`를 확인한다.
- 채널표는 `배정`, `수집대상`, `검토이유`, `사용자코멘트`로 필수·선택·배정 검토·신입생 제외를 구분한다. `수집대상=예`는 현재 조사상 대상이라는 뜻이며 수집기가 구현됐다는 뜻은 아니다.
- 연결표에서 `학과명`을 필터링하면 학교 공통, 소속 대학, 학과·전공 필수 채널이 나온다. 중복 이름은 `학과ID`와 `소속대학`으로 구분한다. 앱은 본인 학과 필수 공지에 다른 학과 필수 공지와 식당을 추가 선택하게 한다.
- ‘없어진듯’ 메모가 있는 4곳은 삭제하지 않고 배정 검토로 보존했다. 해당 미확인 채널의 자동 필수 배정은 보류했고 학교·소속 대학 공통 채널은 유지했다.
- 학부에서 전공으로 나뉘는 3곳은 전공을 선택한 뒤 해당 전공의 공지를 필수 배정한다. 학부에 모든 전공 공지를 일괄 배정하지 않는다.

## 공지 저장 구조 (2026-09-30 확정)

실제 저장은 기존 계획대로 `data/db/notices.json`을 사용한다. DB 서버는 추가하지 않는다. 아래 형식을 `docs/contracts.md`에 확정하고 `collector/store.py`로 구현했다. 국어국문학과 학사공지 첫 페이지의 실제 수집을 연결했으며 기존 `items.json` 계약은 변경하지 않았다. 수집 사용법은 `docs/collection.md`에 있다.

공지 한 건을 한 레코드로 저장한다. 같은 게시판을 여러 학과·채널이 공유해도 원문 글은 한 번 저장한다.

| 필드 | 자료형 | 의미 |
|---|---|---|
| id | 문자열 | 게시판 ID와 원문 글 ID를 결합한 고유 식별자 |
| source_board_id | 문자열 | 원문 게시판 식별자. 페이지 번호·검색 조건·세션 값은 제외 |
| source_post_id | 문자열 | 원문 글 ID. 목록 순번은 사용하지 않음 |
| channel_ids | 문자열 배열 | 이 공지를 제공하는 채널 ID |
| title | 문자열 | 원문 제목 |
| url | 문자열 | 원문 상세 주소 |
| posted_at | 날짜 또는 null | 원문 게시일. 확인하지 못하면 null |
| deadline | 날짜 또는 null | 원문에서 확인한 마감일. 없거나 확인하지 못하면 null |
| body | 문자열 또는 null | 확인한 본문 텍스트. 본문 확인 상태와 함께 사용 |
| body_status | 문자열 | text / image-only / attachment-only / empty / needs-review |
| first_seen_at | 시각 문자열 | 우리 서비스가 처음 발견한 시각 |
| last_checked_at | 시각 문자열 | 마지막 상세 확인에 성공한 시각 |
| content_hash | 문자열 | 제목·본문·게시일·마감일·본문 상태의 변경 감지용 SHA-256 |

날짜는 Asia/Seoul의 `YYYY-MM-DD`, 저장 이력 시각은 `2026-09-30T05:37:00+09:00` 같은 ISO 8601 형식이다. 위 시각은 형식 설명용 예시이며 실제 수집 기록이 아니다.

## 저장·갱신 규칙

1. 처음 발견하면 한 번 추가하고 `first_seen_at`을 유지한다. 첫 운영 때 가져온 과거 공지를 전부 오늘 새 공지로 소개하지 않는다.
2. 같은 게시판·글 ID를 다시 확인하면 기존 레코드를 갱신한다. 내용이 달라지면 해시가 바뀌며 수정으로 판별한다.
3. 마감일과 현재 브리핑 날짜로 `dday`를 계산한다. `dday`, `reason=new/reminder`는 날짜에 따라 바뀌므로 영구 저장값 대신 `items.json` 생성 시 넣는다.
4. 이미지·첨부 전용 본문은 상태를 남기고 읽지 못한 날짜·장소를 채우지 않는다. 정상적인 빈 본문과 파싱 실패를 구분한다.
5. 요청·파싱 실패는 그날 `errors`에 남긴다. 마지막 성공 레코드를 빈 값으로 덮어쓰거나 성공 확인 시각을 갱신하지 않는다. 게시판 일부 실패로 전체 저장을 중단하지 않는다.
6. 저장용 JSON 접근은 `collector/store.py`로 제한하고 임시 파일 작성 후 교체한다. `ensure_ascii=False`, 들여쓰기 2칸, 키 정렬을 유지한다.

내용이 같아도 확인 성공 시각과 채널 연결은 갱신한다. 과거 결과로 최신 레코드를 덮어쓰거나 같은 호출에 상충하는 동일 글을 넣으면 예외를 발생시킨다. 필드와 본문 상태의 자세한 검증 규칙은 `docs/contracts.md`가 기준이다.

## 사용과 오프라인 테스트

프로젝트 폴더에서 `python -m pytest -q`를 실행한다. 테스트는 임시 폴더와 가상의 공지를 사용해 운영 데이터를 만들지 않으며 인터넷을 호출하지 않는다.

코드에서 `from collector.store import load_notices, upsert_notices`로 사용한다. 입력 레코드는 원문 값 9개 필드이며, 고유 ID·최초 발견 시각·마지막 확인 시각·해시는 store가 생성한다. 빈 입력은 파일을 만들지 않는다. 저장 함수가 반환하는 `new/updated/unchanged`는 저장 결과이며 당일 브리핑 선정 결과와 구분한다.

수집기·파서는 다음 단계다. 현재 구현한 저장 기능은 단일 writer용이며 Actions의 일일 실행도 동시에 파일을 갱신하지 않도록 직렬화해야 한다.

## HTML 파서 연결

`collector/knu_cms.py`에서 저장된 KNU CMS 목록·상세 HTML을 파싱하고 `to_notice()` 결과를 `upsert_notices()`에 전달한다. 오프라인 통합 테스트와 제한은 `docs/knu-cms-parser.md`를 참고한다.
